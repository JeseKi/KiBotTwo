# 可阅读性重写工作流

## 目标

复现复测保证 roadmap 能写出正确代码；可阅读性重写保证 roadmap 像一套给学生阅读的工程教材。

当某个 part 已经通过文档复测后，必须再检查它是否存在明显的“补丁感”：为了让 AI Agent 复测通过而加入的审计语言、禁止语、内部实现提示、`.bak` / patch / sub agent 语境，或者章节之间像多次修补后拼接起来，而不是一条自然的教学脉络。

可阅读性重写的目标不是改变实现，而是把已经正确的内容重新梳理成读者能顺着理解的章节。

## 重写者角色

启动一个新的 sub agent，角色设定为：

```text
你是一名大学工程课程老师，正在把一份 AI Agent 反复修补后的工程 roadmap 初稿，重写成学生可以顺着阅读和实践的教程章节。

你的任务不是重新设计实现，也不是删减必要步骤，而是梳理叙事脉络、消除补丁感、把审计语言改写成自然的工程教学语言。

你必须保留原文中的代码片段、文件路径、实现顺序、验证命令、完成边界和关键技术判断。可以调整段落组织、过渡语、解释方式和章节开头/收束，让它读起来像一次完整讲授，而不是复测失败后的补丁清单。
```

## 必须保留

- 原 roadmap 的实现语义。
- 文件路径、代码片段、配置片段、命令和参数。
- 已经通过复测的步骤顺序，除非只是移动解释性段落，不改变操作顺序。
- `roadmap/index.md` 中的系统预期状态、完成边界、失败判读和下一阶段契约。
- reference/checklist/evidence 中承担验收或审计职责的内容。

## 必须消除

roadmap 面向学生，不应该暴露复测机制。以下内容如果出现在 roadmap 主线章节，应改写或移到 evidence：

- `.bak`、`reference-runtime.patch`、patch 字节级一致、sub agent、复测 oracle 等审计语境。
- “不要新增额外 helper/import/test”“不要自由发挥”“不要复制某文件”这类 AI 约束语言。
- “为了让 patch 一致”这类内部验证理由。
- 只对 Agent 有意义、对学生没有解释价值的禁止语。
- 章节之间突兀插入的补丁段落。
- 重复解释同一个限制，但没有新的教学价值。

## 改写原则

把负向约束改成正向教学理由。

示例：

```text
差：本节不要从 `.bak` 文件复制代码。创建空文件后，按下面片段顺序写入；除片段要求外，不新增额外 helper、import 或测试。

好：先创建 `frontier_core.py`。这一节只放入边界检测需要的最小数据结构和纯函数，让算法层先独立稳定下来；ROS2 节点生命周期、topic 订阅和 action 调用会在下一节接入。
```

示例：

```text
差：不要新增额外测试，否则 patch 会不一致。

好：本节的测试只覆盖 frontier 核心算法的三个边界：未知栅格识别、候选点聚类和目标点选择。这样可以先确认算法契约，后续集成测试再覆盖 ROS2 节点行为。
```

示例：

```text
差：必须按 reference-runtime.patch 中的顺序实现。

好：先完成纯算法，再接入节点，最后补 launch。这个顺序能把问题拆开：算法错误先由单元测试暴露，ROS2 接入错误再由节点 smoke test 暴露。
```

## 工作流程

1. 阅读当前 part 的 `roadmap/`、必要 `reference/`、`checklist/` 和 `evidence/usage.md`。
2. 标记 roadmap 中的补丁感段落、审计语言、AI 约束语言和叙事断裂点。
3. 重写 roadmap 章节，使它像老师给学生写的连续教程。
4. 不修改代码片段的语义，不改验证命令，不改完成边界。
5. 如果发现必须改变实现步骤才能读顺，停止并反馈给 main agent；不要自行改实现。
6. 输出修改摘要：哪些段落被重写、哪些审计语境被移除、是否存在可能影响复现的风险。

## 给 readability sub agent 的 prompt 模板

```text
请只做文档可阅读性重写，不做代码实现，不做复现复测。

你是一名大学工程课程老师。当前 roadmap 已经过可复现性复测，但可能带有 AI Agent 多轮补丁后的痕迹。请阅读 docs/<目标>/<part>/roadmap/ 以及必要的 reference/checklist/evidence/usage.md，把 roadmap 重写成学生可以顺着阅读和实践的教程。

要求：
1. 保留原文中的代码片段、文件路径、实现顺序、验证命令、完成边界和关键技术判断。
2. 消除 roadmap 主线中的 `.bak`、reference-runtime.patch、patch 字节级一致、sub agent、oracle、不要新增 helper/import/test 等审计或 AI 约束语言。
3. 把负向限制改写成正向工程理由，例如模块边界、教学顺序、测试分层、后续章节会扩展什么。
4. 让章节有叙事感：说明现在为什么做这一步、它承接了前一节什么、做完后为下一节铺垫什么。
5. 不要把 evidence 的审计职责搬进 roadmap；审计细节留在 evidence。
6. 如果某个段落必须保留审计语言才能保证复现，报告给 main agent，不要硬改。

最终报告：
- 是否完成重写。
- 修改了哪些 roadmap 文件。
- 移除了哪些补丁感/审计感表达。
- 是否存在可能影响复现复测的风险。
```

## 通过标准

- roadmap 读起来像连续教程，而不是复测补丁清单。
- 学生不需要知道 `.bak`、patch、sub agent 或 oracle，就能理解为什么按这个顺序实现。
- 代码片段和验证命令没有被语义改写。
- 重写后必须再执行一次复现复测；只有可阅读性和可复现性都通过，part 才能最终完成。
