# 阶段 02：Nav2 导航接入路线图

## 阶段定位

本阶段承接 `01-SLAM-建图与定位`，目标是让当前 Gazebo 仿真小车具备可验证的点到点导航能力。

阶段 01 的产出应提供：

- `map -> odom -> base_link -> lidar_link` 的可用 TF 链路。
- `/map` 或可加载的静态地图。
- `/scan` 作为 costmap obstacle layer 输入。
- `/odom` 作为 Nav2 odometry 输入。
- `/cmd_vel_raw -> cmd_vel_watchdog -> /cmd_vel` 作为 Nav2 控制输出链路。

如果阶段 01 尚未完成运行时验收，本阶段可以先完成文件计划和配置草案，但不能进入功能完成状态。

## 阶段目标

完成本阶段后，系统应具备：

- 能启动 Gazebo、SLAM 或地图服务、Nav2 lifecycle 节点。
- 能通过 RViz `Nav2 Goal` 或 `NavigateToPose` action 发送目标点。
- Nav2 能基于当前地图和 costmap 规划路径。
- controller 能向 `/cmd_vel_raw` 输出速度，经 `cmd_vel_watchdog` 转发到 `/cmd_vel`，且不被旧控制节点抢占。
- 小车能在障碍物世界中尝试到达目标点。
- 能为 `03-边界探索` 提供“给定目标点即可导航”的稳定接口。

## 采用方案

第一版采用 Nav2 最小 bringup：

- 导航框架：Nav2。
- 全局坐标系：`map`。
- 里程计坐标系：`odom`。
- 机器人基座坐标系：优先使用阶段 01 已确认的 `base_link`。
- 障碍物输入：`/scan`。
- 控制输出：Nav2 controller 输出 remap 到 `/cmd_vel_raw`，由 `cmd_vel_watchdog` 转发到 `/cmd_vel`。
- 第一版运行环境：优先使用 `kibot_one_obstacles.world.sdf`。

本阶段不追求最优导航效果，先验证 Nav2 节点、TF、costmap、planner、controller 和速度输出链路闭合。

## 关键约束

### 控制权归属

Nav2 接入时，第一版保留现有 `cmd_vel_watchdog`，Nav2 controller 不直接写最终 Gazebo 入口 `/cmd_vel`，而是输出到 `/cmd_vel_raw`。当前系统已有：

- `mode_control`
- `follow_controller`
- `cmd_vel_watchdog`
- 可选的 `keyboard_teleop`

因此 Nav2 验证时必须避免多个节点同时向 `/cmd_vel_raw` 发布互相冲突的速度，同时保持 `/cmd_vel` 由 `cmd_vel_watchdog` 统一转发给 Gazebo。

第一版建议：

- 启动 Nav2 验证时关闭 `follow_controller`。
- 关闭 `keyboard_teleop`。
- 增加或使用 `NAV2` 模式，使 `mode_control` 在 Nav2 验证时不主动发布 `/cmd_vel_raw`。
- 保留 `cmd_vel_watchdog`，让 Nav2 输出经 `/cmd_vel_raw -> cmd_vel_watchdog -> /cmd_vel` 进入 Gazebo。
- 只有当 `cmd_vel_watchdog` 实际阻塞或改写 Nav2 正常速度输出时，才把关闭或调整 watchdog 作为 fallback，并记录原因。

### 地图来源

本阶段有两种合法路径：

- 在线 SLAM + Nav2：继续运行 `slam_toolbox`，Nav2 使用实时 `/map`。
- 静态地图 + Nav2：阶段 01 保存地图后，由 `map_server` 加载。

第一版优先使用在线 SLAM + Nav2，因为它承接阶段 01 的当前实现；但如果 Nav2 lifecycle 和 costmap 排查太复杂，可以先保存一张地图做静态地图验证。

### frame 约束

本阶段不重新设计 TF。必须复用阶段 01 已确认的 frame：

```text
map -> odom -> base_link -> lidar_link
```

如果阶段 01 最终没有采用 `base_link`，则 Nav2 参数中的 `robot_base_frame` 必须同步使用实际 base frame，并在 `记录与复盘.md` 记录迁移风险。

## 实施路线

### 02.1 确认阶段 01 输入

开始实现前确认：

- `/map` 是否存在。
- `map -> odom` 是否存在。
- `odom -> base_link` 是否存在。
- `base_link -> lidar_link` 是否存在。
- `/scan` 的 frame 是否能转换到 `base_link`。
- `/cmd_vel` 是否能驱动 Gazebo 小车。

结果记录到 `运行时检查清单.md`。

### 02.2 建立 Nav2 文件边界

第一版建议继续放在 `kibot_one_sim` 中，减少 package 拆分成本：

- `launch/nav2.launch.py`
- `config/nav2_params.yaml`

如果后续导航文件变多，再考虑新增 `kibot_one_navigation` package。

### 02.3 编写最小 Nav2 参数

先只配置能跑通链路的核心项：

- `use_sim_time`
- `global_frame`
- `robot_base_frame`
- `odom_topic`
- local / global costmap
- planner plugin
- controller plugin
- behavior tree navigator
- lifecycle manager

参数调优留到 Nav2 能稳定启动后再做。

### 02.4 启动顺序验证

推荐验证顺序：

```text
Gazebo + bridge
  -> SLAM 或 map_server
    -> Nav2
      -> RViz 发送目标点
```

每一步只引入一个新变量，避免把 TF、地图、costmap 和 controller 问题混在一起。

### 02.5 导航行为验证

通过 RViz 或 action client 发送近距离目标点：

- 第一目标：前方无遮挡短距离目标。
- 第二目标：需要绕过简单障碍物的目标。
- 第三目标：不可达目标，用于观察失败状态。

本阶段只要求能规划并尝试执行，不要求复杂场景下表现稳定。

## 本阶段不做

本阶段不处理：

- frontier 探索。
- 视觉旗帜检测。
- 旗帜位置估计。
- 任务状态机。
- 完整导航参数调优。
- 多机器人或真实机器人部署。
- 重新设计旧 FOLLOW 模式。

旧 `/flag_pose` 链路可以继续存在，但不应参与 Nav2 验证。

## 阶段完成条件

本阶段完成时应满足：

- Nav2 lifecycle 节点能进入 active 状态。
- global costmap 和 local costmap 能正常发布。
- RViz 可显示地图、机器人、costmap 和规划路径。
- `NavigateToPose` goal 能被接收。
- Nav2 能产生 `/cmd_vel_raw`，并经 `cmd_vel_watchdog` 转发为 `/cmd_vel`。
- 小车能对目标点做出实际运动。
- 至少完成一次可复现的短距离导航尝试。
- 已记录阶段 03 调用 Nav2 所需的 action、frame、目标格式和失败状态。

## 后续阶段

完成本阶段后进入：

```text
03-边界探索
```

阶段 03 不应该直接控制 `/cmd_vel`，而应通过 Nav2 的 `NavigateToPose` action 发送探索目标点。
