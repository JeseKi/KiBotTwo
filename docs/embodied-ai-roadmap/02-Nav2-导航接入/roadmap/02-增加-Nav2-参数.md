# 02-建立 Nav2 参数骨架

## 本节目标

本节开始编写：

```text
src/kibot_one_sim/config/nav2_params.yaml
```

不要把它理解成“一口气复制一份 Nav2 示例参数”。我们会从最小的坐标约定开始，一层一层把 Nav2 需要的行为补上：

```text
frame 约定
  -> 行为树 action 入口
  -> controller 和 goal checker
  -> local/global costmap
  -> planner
  -> velocity smoother
  -> collision monitor
```

## 为什么现在做

Nav2 是一组 lifecycle node。每个 node 都会从同一个 YAML 文件里读取自己的参数。如果参数文件里 frame、topic、速度边界不一致，launch 能启动也不代表机器人能导航。

本节需要参考：

- `../reference/nav2-contract.md`
- `../reference/file-plan.md`

## 第一步：先写行为树的坐标约定

Nav2 的 `bt_navigator` 负责暴露 `/navigate_to_pose` 这类 action。它需要知道目标和机器人分别在哪些 frame 中解释。

先写最小片段：

```yaml
bt_navigator:
  ros__parameters:
    global_frame: map
    robot_base_frame: base_link
    odom_topic: /odom
```

这三行先建立最核心的约定：

- `global_frame: map` 表示导航目标使用地图坐标。
- `robot_base_frame: base_link` 表示机器人本体用 `base_link` 表达。
- `odom_topic: /odom` 表示行为树可以读取里程计状态。

接下来告诉 `bt_navigator` 需要启用哪些 navigator：

```yaml
bt_navigator:
  ros__parameters:
    global_frame: map
    robot_base_frame: base_link
    odom_topic: /odom
    navigators: ["navigate_to_pose", "navigate_through_poses"]
    navigate_to_pose:
      plugin: "nav2_bt_navigator::NavigateToPoseNavigator"
    navigate_through_poses:
      plugin: "nav2_bt_navigator::NavigateThroughPosesNavigator"
```

阶段 03 会主要依赖 `navigate_to_pose`。这里保留 `navigate_through_poses`，是为了后续 waypoint 编排不需要重新换参数结构。

最后加上错误码名称：

```yaml
bt_navigator:
  ros__parameters:
    error_code_names:
      - compute_path_error_code
      - follow_path_error_code
```

这让行为树结果里能携带规划和路径跟随阶段的错误来源。后面看到 `error_code: 105` 时，我们就能把它判读为 `FollowPath` 的 `FAILED_TO_MAKE_PROGRESS`，而不是误以为 action server 没接上。

## 第二步：让 controller 知道怎样判断进展和到达

现在写 `controller_server` 的最小骨架：

```yaml
controller_server:
  ros__parameters:
    controller_frequency: 20.0
    controller_plugins: ["FollowPath"]
```

这表示 controller 每秒计算 20 次速度，并加载一个名叫 `FollowPath` 的控制器插件。

接下来加入进展检查：

```yaml
controller_server:
  ros__parameters:
    progress_checker_plugins: ["progress_checker"]
    progress_checker:
      plugin: "nav2_controller::SimpleProgressChecker"
      required_movement_radius: 0.5
      movement_time_allowance: 10.0
```

这段配置定义了“什么叫没有进展”：

- `required_movement_radius: 0.5` 表示机器人需要移动至少 0.5m。
- `movement_time_allowance: 10.0` 表示如果 10 秒内没有达到这个移动量，就可能判定失败。

所以当 action 返回 `error_code: 105` 时，它通常不是“目标没发出去”，而是 controller 认为机器人没有稳定移动。

再加入 goal checker：

```yaml
controller_server:
  ros__parameters:
    goal_checker_plugins: ["general_goal_checker"]
    general_goal_checker:
      stateful: True
      plugin: "nav2_controller::SimpleGoalChecker"
      xy_goal_tolerance: 0.10
      yaw_goal_tolerance: 0.25
```

这里定义“什么叫到达目标”：

- 平面位置误差小于约 `0.10m`。
- 朝向误差小于约 `0.25rad`。

验证 `map` 坐标目标误差时，不要用 `/odom` 直接相减，要用：

```bash
ros2 run tf2_ros tf2_echo map base_link
```

因为目标是 `frame_id: map`，而 `/odom` 是另一个坐标系。

## 第三步：给 MPPI controller 加速度边界

现在把 `FollowPath` 具体指定为 MPPI controller：

```yaml
controller_server:
  ros__parameters:
    FollowPath:
      plugin: "nav2_mppi_controller::MPPIController"
      motion_model: "DiffDrive"
```

`motion_model: "DiffDrive"` 很关键。KiBotTwo 的 Gazebo 模型是差速车，不应该让 controller 生成横向平移。

接下来收敛速度：

```yaml
controller_server:
  ros__parameters:
    FollowPath:
      vx_max: 0.45
      vx_min: -0.20
      vy_max: 0.5
      wz_max: 1.2
```

这里的 `vx` 是前后线速度，`wz` 是绕 z 轴旋转速度。虽然 MPPI 参数里存在 `vy_max`，但后续 velocity smoother 会把 y 方向速度限制为 0，保证进入 Gazebo 的速度符合差速模型。

再加入加速度边界：

```yaml
controller_server:
  ros__parameters:
    FollowPath:
      ax_max: 0.8
      ax_min: -0.8
      az_max: 1.5
```

这些值不追求快，而是先保证仿真稳定。阶段 02 的目标是接通导航闭环，不是调出最高速度。

## 第四步：先建立 local costmap

local costmap 用来让 controller 看见机器人附近的障碍物。它使用局部稳定坐标系 `odom`：

```yaml
local_costmap:
  local_costmap:
    ros__parameters:
      global_frame: odom
      robot_base_frame: base_link
      rolling_window: true
```

这里的 `global_frame: odom` 不是全局地图，而是局部代价地图的参考坐标。`rolling_window: true` 表示窗口跟着机器人移动。

接下来设置窗口大小和分辨率：

```yaml
local_costmap:
  local_costmap:
    ros__parameters:
      width: 3
      height: 3
      resolution: 0.05
      robot_radius: 0.34
```

`robot_radius: 0.34` 是阶段 02 的保守近似，用圆形 footprint 覆盖当前车体平面尺寸。

最后加入激光障碍物层：

```yaml
local_costmap:
  local_costmap:
    ros__parameters:
      plugins: ["voxel_layer", "inflation_layer"]
      voxel_layer:
        plugin: "nav2_costmap_2d::VoxelLayer"
        observation_sources: scan
        scan:
          topic: /scan
          data_type: "LaserScan"
          clearing: True
          marking: True
      inflation_layer:
        plugin: "nav2_costmap_2d::InflationLayer"
        inflation_radius: 0.70
```

`voxel_layer` 负责把 `/scan` 里的障碍物写入局部代价地图；`inflation_layer` 给障碍物周围留安全距离。

## 第五步：建立适合探索前置阶段的 global costmap

global costmap 使用 `map`：

```yaml
global_costmap:
  global_costmap:
    ros__parameters:
      global_frame: map
      robot_base_frame: base_link
      robot_radius: 0.34
```

接下来使用 rolling window：

```yaml
global_costmap:
  global_costmap:
    ros__parameters:
      rolling_window: true
      width: 20
      height: 20
      track_unknown_space: false
```

这里是阶段 02 的关键取舍。SLAM 初始地图很小，如果直接使用静态全局地图层，目标很容易落在 unknown 或地图外。阶段 02 先用 rolling obstacle/inflation 支撑点到点导航入口，完整 frontier 探索放到阶段 03。

然后加入全局障碍层：

```yaml
global_costmap:
  global_costmap:
    ros__parameters:
      plugins: ["obstacle_layer", "inflation_layer"]
      obstacle_layer:
        plugin: "nav2_costmap_2d::ObstacleLayer"
        observation_sources: scan
        scan:
          topic: /scan
          data_type: "LaserScan"
          clearing: True
          marking: True
      inflation_layer:
        plugin: "nav2_costmap_2d::InflationLayer"
        inflation_radius: 0.7
```

这让 planner 能基于当前激光观测绕开局部障碍，但它仍然不等价于完整探索系统。

## 第六步：加入 planner

现在配置 planner server：

```yaml
planner_server:
  ros__parameters:
    planner_plugins: ["GridBased"]
    GridBased:
      plugin: "nav2_navfn_planner::NavfnPlanner"
```

`GridBased` 是这个 planner 插件的名字，后续行为树会请求它生成路径。

再加入容差和 unknown 策略：

```yaml
planner_server:
  ros__parameters:
    GridBased:
      tolerance: 0.10
      use_astar: false
      allow_unknown: true
```

`tolerance: 0.10` 和 goal checker 的 `xy_goal_tolerance` 对齐，避免过大的容差导致“没有明显移动也成功”的假象。

## 第七步：让速度进入 smoother

Nav2 controller 原始速度不是直接给 Gazebo，而是先交给 smoother：

```yaml
velocity_smoother:
  ros__parameters:
    smoothing_frequency: 20.0
    feedback: "OPEN_LOOP"
```

然后限制输出速度：

```yaml
velocity_smoother:
  ros__parameters:
    max_velocity: [0.45, 0.0, 1.2]
    min_velocity: [-0.20, 0.0, -1.2]
    max_accel: [0.8, 0.0, 1.5]
    max_decel: [-0.8, 0.0, -1.5]
```

这里第二个分量是 y 方向速度，设置为 `0.0`。这一步把 MPPI 可能产生的横向速度收敛掉，确保最终桥接到 Gazebo 的速度适合差速车。

Jazzy 的 `navigation_launch.py` 还会启动 `smoother_server`。虽然阶段 02 不主动调用路径平滑 action，也需要给它一个最小插件配置，否则 lifecycle bringup 可能在这个节点上中断：

```yaml
smoother_server:
  ros__parameters:
    smoother_plugins: ["simple_smoother"]
    simple_smoother:
      plugin: "nav2_smoother::SimpleSmoother"
      tolerance: 1.0e-10
      max_its: 1000
      do_refinement: True
```

## 第八步：补齐 Jazzy bringup 的辅助节点

当前 Jazzy 的 `nav2_bringup` 不只启动 controller、planner、BT navigator 和 velocity smoother。它还会启动 `behavior_server`、`waypoint_follower`、`route_server` 和 `docking_server`。这些节点不是阶段 02 的业务入口，但它们属于同一个 lifecycle manager；只要其中一个配置缺失，`Managed nodes are active` 就不会出现。

先补 `behavior_server`，让恢复行为有 frame、costmap 和插件入口：

```yaml
behavior_server:
  ros__parameters:
    local_costmap_topic: local_costmap/costmap_raw
    global_costmap_topic: global_costmap/costmap_raw
    local_footprint_topic: local_costmap/published_footprint
    global_footprint_topic: global_costmap/published_footprint
    cycle_frequency: 10.0
    behavior_plugins: ["spin", "backup", "drive_on_heading", "assisted_teleop", "wait"]
    spin:
      plugin: "nav2_behaviors::Spin"
    backup:
      plugin: "nav2_behaviors::BackUp"
    drive_on_heading:
      plugin: "nav2_behaviors::DriveOnHeading"
    assisted_teleop:
      plugin: "nav2_behaviors::AssistedTeleop"
    wait:
      plugin: "nav2_behaviors::Wait"
    local_frame: odom
    global_frame: map
    robot_base_frame: base_link
    transform_tolerance: 0.1
    simulate_ahead_time: 2.0
    max_rotational_vel: 1.0
    min_rotational_vel: 0.4
    rotational_acc_lim: 3.2
```

再补 waypoint follower。阶段 03 主要用 `NavigateToPose`，但 bringup 会同时管理 waypoint follower，所以这里给它一个等待任务插件：

```yaml
waypoint_follower:
  ros__parameters:
    loop_rate: 20
    stop_on_failure: false
    action_server_result_timeout: 900.0
    waypoint_task_executor_plugin: "wait_at_waypoint"
    wait_at_waypoint:
      plugin: "nav2_waypoint_follower::WaitAtWaypoint"
      enabled: True
      waypoint_pause_duration: 200
```

再补 route server。阶段 02 不使用 route graph，但 Jazzy bringup 会配置它，所以保留空 graph 的默认行为，并明确 route operation 和 cost function 插件：

```yaml
route_server:
  ros__parameters:
    boundary_radius_to_achieve_node: 1.0
    radius_to_achieve_node: 2.0
    smooth_corners: true
    operations: ["AdjustSpeedLimit", "ReroutingService", "CollisionMonitor"]
    ReroutingService:
      plugin: "nav2_route::ReroutingService"
    AdjustSpeedLimit:
      plugin: "nav2_route::AdjustSpeedLimit"
    CollisionMonitor:
      plugin: "nav2_route::CollisionMonitor"
      max_collision_dist: 3.0
    edge_cost_functions: ["DistanceScorer", "CostmapScorer"]
    DistanceScorer:
      plugin: "nav2_route::DistanceScorer"
    CostmapScorer:
      plugin: "nav2_route::CostmapScorer"
```

最后补 docking server。阶段 02 不执行 dock action，但 Jazzy bringup 会把 `docking_server` 纳入 lifecycle，缺少 dock plugin 或 controller 配置时会影响整体激活：

```yaml
docking_server:
  ros__parameters:
    controller_frequency: 50.0
    initial_perception_timeout: 5.0
    wait_charge_timeout: 5.0
    dock_approach_timeout: 30.0
    undock_linear_tolerance: 0.05
    undock_angular_tolerance: 0.1
    max_retries: 3
    base_frame: "base_link"
    fixed_frame: "odom"
    dock_backwards: false
    dock_prestaging_tolerance: 0.5
    dock_plugins: ['simple_charging_dock']
    simple_charging_dock:
      plugin: 'opennav_docking::SimpleChargingDock'
      docking_threshold: 0.05
      staging_x_offset: -0.7
      use_external_detection_pose: true
      use_battery_status: false
      use_stall_detection: false
      external_detection_timeout: 1.0
      external_detection_translation_x: -0.18
      external_detection_translation_y: 0.0
      external_detection_rotation_roll: -1.57
      external_detection_rotation_pitch: -1.57
      external_detection_rotation_yaw: 0.0
      filter_coef: 0.1
    controller:
      k_phi: 3.0
      k_delta: 2.0
      v_linear_min: 0.15
      v_linear_max: 0.15
      use_collision_detection: true
      costmap_topic: "local_costmap/costmap_raw"
      footprint_topic: "local_costmap/published_footprint"
      transform_tolerance: 0.1
      projection_time: 5.0
      simulation_step: 0.1
      dock_collision_threshold: 0.3
```

这些配置的目的不是让阶段 02 开始做 waypoint、route 或 dock，而是保证 Nav2 官方 bringup 中被 lifecycle manager 管理的节点都能完成 configure/activate。

## 第九步：加入碰撞监控

collision monitor 放在速度链路旁边，用来在接近障碍时限制运动：

```yaml
collision_monitor:
  ros__parameters:
    base_frame_id: "base_link"
    odom_frame_id: "odom"
    cmd_vel_in_topic: "cmd_vel_smoothed"
    cmd_vel_out_topic: "cmd_vel"
```

这段配置说明它读取平滑速度，并能发布监控后的速度。当前阶段 Gazebo bridge 直接订阅 `/cmd_vel_smoothed`，所以 collision monitor 的日志更多用于观察“是否接近碰撞”，而不是阶段 02 的主控制入口。

再加入 footprint approach：

```yaml
collision_monitor:
  ros__parameters:
    polygons: ["FootprintApproach"]
    FootprintApproach:
      type: "polygon"
      action_type: "approach"
      footprint_topic: "/local_costmap/published_footprint"
      time_before_collision: 1.2
```

Jazzy 的 collision monitor 还必须知道自己从哪里读取障碍物观测。继续加入 `/scan` observation source：

```yaml
collision_monitor:
  ros__parameters:
    state_topic: "collision_monitor_state"
    transform_tolerance: 0.2
    source_timeout: 1.0
    base_shift_correction: True
    stop_pub_timeout: 2.0
    FootprintApproach:
      simulation_time_step: 0.1
      min_points: 6
      visualize: False
      enabled: True
    observation_sources: ["scan"]
    scan:
      type: "scan"
      topic: "scan"
      min_height: 0.15
      max_height: 2.0
      enabled: True
```

如果这里缺少 `observation_sources`，启动时会看到：

```text
parameter 'observation_sources' is not initialized
```

这不是运行依赖问题，也不是 lifecycle manager 本身坏了，而是 `collision_monitor` 参数没有写完整。

当你看到日志里出现：

```text
Robot to approach for 1.200000 seconds away from collision
```

它表示机器人接近障碍物，Nav2 可能进入更保守的行为。远端目标不稳定时，这条日志和 `Failed to make progress` 常常一起出现。

## 做完应该看到什么

构建后启动：

```bash
ros2 launch kibot_one_sim nav2.launch.py use_rviz:=false
```

再检查：

```bash
ros2 lifecycle get /controller_server
ros2 lifecycle get /planner_server
ros2 lifecycle get /bt_navigator
```

预期都返回：

```text
active [3]
```

如果 controller 或 planner 没有 active，优先看 YAML 缩进和插件名。Nav2 参数文件里同名 node、`ros__parameters`、插件列表和插件块必须对齐。

## 本节小结

本节不是为了把 Nav2 所有参数调到最优，而是建立阶段 02 的最小导航参数骨架：

- `map / odom / base_link` frame 约定明确。
- `/scan` 进入 local/global costmap。
- controller 有进展检查和到达判定。
- planner 可以生成路径。
- smoother 输出差速车可接受的速度。
- Jazzy bringup 的辅助 lifecycle nodes 都有最小配置，避免整体激活被非主线节点阻断。

下一节把这些参数接到一个统一 launch 入口里。
