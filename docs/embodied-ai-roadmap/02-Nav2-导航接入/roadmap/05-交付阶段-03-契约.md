# 05-交付阶段 03 导航契约

## 本节目标

本节把阶段 02 已经验证的 Nav2 能力，收束成阶段 03 可以依赖的接口契约。

阶段 03 要做的是 frontier 选择和探索任务管理。它不应该重新理解 Nav2 的 controller、costmap 或 velocity smoother。

## 为什么现在做

如果没有契约，阶段 03 很容易写出这种代码：

```python
# 反例：探索模块直接依赖 Nav2 内部节点状态
if controller_server_active and planner_server_active and local_costmap_ok:
    send_goal(frontier)
```

这会让探索模块和 Nav2 内部实现耦合太深。阶段 03 应该依赖更小的接口：

```text
发送 map 坐标目标
等待 action 结果
解释成功、失败、取消、超时
```

本节需要参考：

- `../reference/nav2-contract.md`
- `../evidence/usage.md`

## 第一条契约：目标只通过 NavigateToPose 发送

阶段 03 使用的 action 名称是：

```text
/navigate_to_pose
```

目标类型是：

```text
nav2_msgs/action/NavigateToPose
```

最小目标长这样：

```yaml
pose:
  header:
    frame_id: map
  pose:
    position:
      x: 0.5
      y: 0.0
      z: 0.0
    orientation:
      w: 1.0
```

这里先只看结构：

- `pose.header.frame_id` 定义目标坐标系。
- `pose.pose.position` 定义目标点。
- `pose.pose.orientation` 定义目标朝向。

阶段 03 生成 frontier 后，应该把 frontier 转成 `map` 坐标下的 `PoseStamped`，再发给 `/navigate_to_pose`。

## 第二条契约：目标坐标是 map 绝对坐标

先看一个容易误解的目标：

```bash
ros2 action send_goal /navigate_to_pose nav2_msgs/action/NavigateToPose \
  "{pose: {header: {frame_id: map}, pose: {position: {x: -5.0, y: 0.0, z: 0.0}, orientation: {w: 1.0}}}}"
```

这里的 `x: -5.0` 不是“向后走 5m”，而是：

```text
map 坐标系中的 x = -5.0
```

所以阶段 03 不能把 frontier 当成相对位移。它必须维护或读取 frontier 在 `map` 中的位置。

目标完成后，验证位置也要用：

```bash
ros2 run tf2_ros tf2_echo map base_link
```

而不是直接用 `/odom` 和目标相减。

## 第三条契约：探索模块只发送局部可达候选

阶段 02 证明了近距离局部可达点可以执行，不证明任意远端绝对坐标都稳定成功。

因此阶段 03 选点时应该先做最小过滤：

```text
frontier 候选
  -> 在 map 中
  -> 不是已知障碍
  -> 距离机器人不过远
  -> 尽量位于当前可观测或可规划区域附近
  -> 再发送 NavigateToPose
```

这里不是要求阶段 03 一开始就有完美探索算法，而是要求它不要把明显穿过障碍物带的远点直接当作验收目标。

## 第四条契约：成功结果表示当前目标完成

当 action 返回：

```text
Goal finished with status: SUCCEEDED
error_code: 0
```

阶段 03 可以认为当前 frontier 目标完成。

这时探索模块可以做三件事之一：

```text
继续选择下一个 frontier
更新已探索区域
如果视觉模块发现旗帜，则切换任务状态
```

不要从 `SUCCEEDED` 推断“整张地图探索完毕”。它只表示这一个目标点完成。

## 第五条契约：失败结果表示目标需要降权或冷却

当 action 返回 `ABORTED` 时，阶段 03 不应该立即退出整个任务。它应该把当前目标标记为暂时不可用，再选择下一个候选。

例如 `105`：

```text
error_code: 105
```

对应 `FollowPath` 的：

```text
FAILED_TO_MAKE_PROGRESS
```

这说明 Nav2 在跟随路径时没有稳定前进。阶段 03 可以把该 frontier 放入冷却列表：

```python
failed_frontiers[frontier_id] = {
    "reason": "failed_to_make_progress",
    "cooldown_until": now + cooldown_duration,
}
```

这段伪代码表达的是策略，不要求直接照抄实现。重点是：失败目标不要立刻反复发送，否则机器人会在同一个不可达区域来回恢复。

## 第六条契约：视觉发现可以取消导航目标

阶段 03 和后续视觉阶段会出现这种情况：

```text
机器人正在探索
  -> 视觉检测发现旗帜
  -> 当前探索目标不再重要
  -> 取消 NavigateToPose goal
  -> 进入靠近或停止逻辑
```

所以探索模块必须把“取消”当作正常路径，而不是错误。

契约上可以写成：

```text
cancel requested by mission manager
  -> cancel current /navigate_to_pose goal
  -> do not mark frontier as failed
```

取消和失败不同：

- 失败说明目标执行不了。
- 取消说明任务目标变了。

## 第七条契约：超时由探索模块主动处理

Nav2 自己会做恢复，但阶段 03 不能无限等一个目标。

阶段 03 应该给每个 frontier goal 设置超时：

```text
send goal
  -> wait until succeeded / aborted / canceled
  -> if timeout, cancel goal
  -> choose next frontier
```

超时不是 Nav2 接入失败。它是探索策略的一部分。

## 第八条契约：阶段 03 不依赖这些内部细节

阶段 03 不应该直接依赖：

```text
/local_costmap/costmap
/global_costmap/costmap
controller_server 内部插件
planner_server 内部插件
velocity_smoother 参数
collision_monitor 状态
```

这些内容可以用于调试，但不应该成为探索模块业务逻辑的必要输入。

阶段 03 应该依赖：

```text
/map
map -> base_link
/navigate_to_pose
action result
```

这样 Nav2 参数后续调优时，探索模块不需要跟着重写。

## 做完应该看到什么

读完本节后，阶段 03 的实现边界应该很清楚：

- frontier 选择模块负责给出 `map` 坐标目标。
- Nav2 负责执行目标。
- mission manager 负责处理成功、失败、取消和超时。
- 远端不可达目标不是阶段 02 的失败，而是阶段 03 需要规避和恢复的输入。

## 本节小结

阶段 02 交付给阶段 03 的不是某个 YAML 文件，而是一个导航执行契约：

```text
给我一个局部可达的 map 坐标目标；
我通过 /navigate_to_pose 尝试执行；
我返回成功、失败、取消或超时信号；
探索模块根据结果选择下一个动作。
```

下一阶段可以开始设计 frontier 发现和目标执行器。
