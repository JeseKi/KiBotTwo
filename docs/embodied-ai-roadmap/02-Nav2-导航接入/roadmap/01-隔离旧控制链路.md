# 01-明确导航控制权

## 本节目标

本节先解决一个比 Nav2 参数更靠前的问题：谁有权控制机器人运动。

阶段 00 的旧系统里，机器人速度链路是：

```text
follow_controller / keyboard_teleop / cruise
  -> /cmd_vel_raw
  -> cmd_vel_watchdog
  -> /cmd_vel
  -> ros_gz_bridge
  -> /model/kibot_one_base/cmd_vel
```

Nav2 接入后，如果继续让旧节点和 Nav2 同时控制 `/cmd_vel`，机器人会出现两个问题：

- action 已经 `SUCCEEDED` 或 `ABORTED`，但机器人实际运动被旧节点覆盖。
- Nav2 controller 正在避障，旧 FOLLOW / MANUAL / CRUISE 又发布了另一条速度。

所以本节不先写 Nav2 参数，而是先建立一个规则：**在 `nav2.launch.py` 这个入口里，Nav2 是唯一导航控制源。**

## 为什么现在做

Nav2 的 planner 和 controller 只在它拥有速度控制权时才有意义。如果速度链路没有隔离，后面的 lifecycle、costmap、goal checker 都可能看起来正常，但机器人行为仍然不可解释。

本节需要参考：

- `../reference/control-ownership.md`
- `../reference/nav2-contract.md`

## 先看旧 bridge 是怎么控制 Gazebo 的

速度最终进入 Gazebo 的地方在：

```text
src/kibot_one_sim/config/ros_gz_bridge.yaml
```

最小速度桥接项长这样：

```yaml
- ros_topic_name: "/cmd_vel"
  gz_topic_name: "/model/kibot_one_base/cmd_vel"
  ros_type_name: "geometry_msgs/msg/Twist"
  gz_type_name: "gz.msgs.Twist"
  direction: ROS_TO_GZ
```

这里的意思是：

- ROS 侧有人发布 `/cmd_vel`。
- `ros_gz_bridge` 把它转成 Gazebo 的 `gz.msgs.Twist`。
- Gazebo DiffDrive plugin 订阅 `/model/kibot_one_base/cmd_vel` 后驱动车体。

这对旧 FOLLOW 演示是合理的，因为旧控制链路的最终输出就是 `/cmd_vel`。

但 Nav2 默认不是这样工作。当前阶段使用的是 Nav2 的 velocity smoother，速度会先经过平滑器：

```text
controller_server / behavior_server
  -> /cmd_vel_nav
  -> velocity_smoother
  -> /cmd_vel_smoothed
```

因此，阶段 02 的 Gazebo 入口应该改为订阅平滑后的速度。

## 把 Gazebo 入口交给 Nav2 平滑速度

现在只改 bridge 的第一项，把 ROS topic 从 `/cmd_vel` 改成 `/cmd_vel_smoothed`：

```yaml
- ros_topic_name: "/cmd_vel_smoothed"
  gz_topic_name: "/model/kibot_one_base/cmd_vel"
  ros_type_name: "geometry_msgs/msg/Twist"
  gz_type_name: "gz.msgs.Twist"
  direction: ROS_TO_GZ
```

这一小段配置建立了阶段 02 的速度归属：

- `/cmd_vel_smoothed` 是 Nav2 velocity smoother 的输出。
- Gazebo 不再直接吃旧链路的 `/cmd_vel`。
- 旧 `cmd_vel_watchdog` 即使还存在于别的 launch 中，也不会通过 `nav2.launch.py` 参与控制。

注意这里没有删除旧系统能力。`kibot_one.launch.py` 仍然可以保留旧 FOLLOW 演示；我们只是让新的 Nav2 入口使用另一条更清晰的速度链路。

## 再设计新的 launch 入口

现在先不要把 Nav2 塞进旧的 `kibot_one.launch.py`。旧入口会启动旧控制节点，它的职责已经和阶段 02 冲突。

我们要新建：

```text
src/kibot_one_sim/launch/nav2.launch.py
```

这个文件一开始只需要表达一个结构：

```python
from launch import LaunchDescription


def generate_launch_description() -> LaunchDescription:
    return LaunchDescription([])
```

这段代码什么都没启动，但它先建立了 ROS2 launch 文件的基本形状：

- `generate_launch_description()` 是 ROS2 launch 系统会调用的入口函数。
- `LaunchDescription([])` 表示这个 launch 暂时没有 action。

接下来我们再逐步往里面加入仿真、SLAM 和 Nav2。

## 明确旧控制节点不属于这个入口

在写 `nav2.launch.py` 时，本节最重要的不是“加什么”，而是“不加什么”。

这些节点不应该出现在 `nav2.launch.py` 里：

```text
mode_control
follow_controller
keyboard_teleop
cmd_vel_watchdog
```

原因分别是：

- `mode_control` 负责旧模式系统，不负责 Nav2 lifecycle。
- `follow_controller` 会绕过 Nav2 直接根据旗帜位姿控制机器人。
- `keyboard_teleop` 是手动速度源。
- `cmd_vel_watchdog` 属于旧 `/cmd_vel_raw -> /cmd_vel` 链路。

因此这一节完成后，`nav2.launch.py` 的设计原则是：

```text
只启动导航所需的仿真、bridge、SLAM 和 Nav2；
不启动任何旧速度控制节点。
```

## 做完应该看到什么

检查 bridge 配置：

```bash
rg -n 'cmd_vel_smoothed|model/kibot_one_base/cmd_vel' src/kibot_one_sim/config/ros_gz_bridge.yaml
```

应该能看到 `/cmd_vel_smoothed` 对应 Gazebo 的 `/model/kibot_one_base/cmd_vel`。

启动后也可以用：

```bash
ros2 topic info /cmd_vel_smoothed -v
```

预期结果是 `kibot_one_bridge` 作为 subscriber 出现在 `/cmd_vel_smoothed` 上。

如果你看到 bridge 仍然订阅 `/cmd_vel`，说明本节还没有完成。继续往后调 Nav2 参数没有意义，因为机器人实际吃到的不是 Nav2 平滑速度。

## 本节小结

本节只建立一个工程事实：阶段 02 的导航入口里，机器人运动由 Nav2 的 `/cmd_vel_smoothed` 控制。

下一节再开始写 `nav2_params.yaml`，让 Nav2 知道坐标系、代价地图、控制器和速度边界。
